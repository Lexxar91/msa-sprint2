# Task2 — миграция BookingService в микросервис (Strangler Fig)

## Что сделано
- `booking-service` (Python 3.14, gRPC :9090): контракт `booking.proto`, своя БД `booking-db`,
  валидации и расчёт цены зеркалят монолит, данные — через REST монолита.
- Монолит переключён на проксирование `POST /api/bookings` → gRPC (`BOOKING_SERVICE_EXTERNAL_*`).
- Событие `BookingCreated` публикуется в RabbitMQ (topic `bookings`, routing `booking.created`).
- `booking-history-service` слушает очередь и строит статистику в отдельной `history-db`
  (view'ы по пользователям/отелям/дням), без нагрузки на боевую БД.

## Стратегия миграции данных при запуске нового сервиса
1. Новый сервис владеет своей БД; схема создаётся идемпотентно (`CREATE TABLE IF NOT EXISTS`) при старте.
2. Старая БД монолита сразу НЕ мигрируется: исторические брони остаются в `monolith-db`
   и доступны монолиту на чтение (`GET /api/bookings` работает как раньше).
3. Запись — только в новую систему («single-write в новое, dual-read со старым»): новые брони
   идут в `booking-db`, пока монолит ещё обслуживает чтение.
4. Аналитика — через события: consumer идемпотентен (`ON CONFLICT DO NOTHING`), что защищает
   от дублей при at-least-once доставке из RabbitMQ.
5. Бэкфил на этом этапе не требуется; он нужен только при полном отключении монолита (см. To Be).

## Стратегия To Be
- Полный вынос доменов в микросервисы, у каждого — своя БД; монолит выводится из пути записи,
  затем из пути чтения, после чего выполняется бэкфил истории и архив монолитной БД.
- Синхронное взаимодействие — gRPC/REST, асинхронное — событийная шина.
- GraphQL Federation для фронтенда (Task3), CI/CD + Kubernetes (Task4), Istio traffic-management (Task5).
