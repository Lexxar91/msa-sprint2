# ADR-001: Миграция BookingService в микросервис на Python 3.14 + FastAPI с RabbitMQ

## Status
Accepted

## Context
Hotelio — онлайн-платформа бронирования жилья (~1 млн пользователей), основной трафик — поиск и бронирование.
Система построена как Java Spring Boot монолит: все модули (Booking, Hotel, User, PromoCode, Review)
живут в одном деплой-юните и используют одну базу PostgreSQL. Синхронная связь внутри монолита —
прямые вызовы сервисов; асинхронная инфраструктура в целевом состоянии бизнеса — масштабируемый брокер сообщений.

## Problem
- Любое изменение в `BookingService` требует полной сборки и регрессионного тестирования всего монолита.
- Невозможно масштабировать только логику бронирования при пиковых нагрузках (основной трафик — именно бронирования).
- Аналитика не может читать данные о бронированиях: прямой доступ к боевой БД создаёт риск для OLTP-нагрузки.
- Плотная связанность модулей тормозит независимую разработку и релизы.

## Options
1. **Оставить всё в монолите** — нулевые затраты, но сохраняются все проблемы связности и масштабирования.
2. **Вынести на Java + Kafka** — соответствует текущему стеку и целевому состоянию, но не даёт выигрыша в скорости итераций и независимости команд.
3. **Вынести на Python 3.14 + FastAPI + RabbitMQ** — быстрая итерация, нативная асинхронность, низкий порог входа, простой в эксплуатации брокер.

## Decision
Выбираем вариант 3.

- **Язык:** Python 3.14 — актуальная версия с поддержкой async/await и свободных потоков (free-threaded).
- **Фреймворк:** FastAPI — высокая производительность, автодокументация (OpenAPI), нативная типизация через Pydantic v2.
- **Синхронная интеграция:** gRPC — монолит вызывает `booking-service` по контракту `booking.proto` (соответствует ТЗ).
- **Асинхронная интеграция:** RabbitMQ — публикация событий `BookingCreated` / `BookingUpdated` через topic exchange.
- **Первый модуль:** `BookingService`, потому что:
  - имеет чёткие входные/выходные контракты;
  - минимально зависит от других модулей (только *читает* данные отелей, пользователей, промокодов);
  - бизнес-критичен — его масштабирование даёт наибольший ROI на основном трафике.

### Отклонение от исходного ТЗ (Kafka → RabbitMQ)
В исходной инфраструктуре заявлена Kafka. Для данного этапа миграции осознанно выбран RabbitMQ.

**Почему RabbitMQ подходит для текущей задачи:**
- Задача `booking-history-service` — реактивная обработка событий бронирования и подсчёт статистики.
  Это классический паттерн «producer → exchange → queue → consumer», который RabbitMQ закрывает из коробки.
- Проще эксплуатация: не требует отдельного координатора (Zookeeper/KRaft), меньше движущихся частей.
- Надёжные гарантии доставки: publisher confirm, ручные ACK/NACK, Dead Letter Exchange (DLQ) для битых событий.
- Для текущего объёма событий (бронирования, а не кликовый поток) пропускной способности RabbitMQ достаточно.

**Чем платим (честно):**
- Kafka — это распределённый лог событий: события можно *перечитать* (replay) с нужного офсета.
  В RabbitMQ событие удаляется из очереди после ACK — повторное потребление требует отдельного хранения.
- Kafka лучше подходит для долгосрочного хранения событий и очень высоких throughput-нагрузок.

**Mitigation (смягчение риска):**
- Контракт событий (`BookingCreated`, `BookingUpdated`) проектируется брокер-независимым (JSON-схема).
  При росте нагрузки переход на Kafka потребует замены транспорта, но не перепроектирования событий.
- Для аналитики, требующей replay, события дополнительно сохраняются в `history_db` — источник правды для отчётов.
- Решение пересматривается при выходе на целевое состояние бизнеса (через год), где заявлена масштабируемая Kafka-инфраструктура.

### Риски Python 3.14 и их mitigation
- Экосистема ещё догоняет 3.14: используем только свежие версии библиотек
  (`grpcio` ≥ 1.81 — первая версия с официальной поддержкой 3.14; `aio-pika` для RabbitMQ).
- Pydantic v1 несовместим с 3.14 — фиксируем Pydantic v2 (FastAPI использует его по умолчанию).
- Все зависимости фиксируем в `requirements.txt` / `pyproject.toml` для воспроизводимости сборки.

## Plan (Strangler Fig)
1. Разработать `booking-service` на Python 3.14 с gRPC-сервером по контракту `booking.proto`.
2. Настроить монолит как фасад: проксировать `POST /api/bookings` → `booking-service:9090` по gRPC
   (переменные `BOOKING_SERVICE_EXTERNAL_HOST` / `BOOKING_SERVICE_EXTERNAL_PORT`).
3. Данные для валидации (отель, пользователь, промокод) `booking-service` получает из монолита по REST —
   без переноса чужой бизнес-логики.
4. `booking-service` публикует событие `BookingCreated` в RabbitMQ.
5. Поднять `booking-history-service`: подписка на события, асинхронный подсчёт статистики в отдельной БД,
   без нагрузки на боевую.
6. Вся новая функциональность по бронированиям пишется только в `booking-service`.
7. Старая логика бронирования в монолите переводится в режим «только чтение» и удаляется после стабилизации.

## Consequences
**Плюсы:**
- Независимый деплой и масштабирование `booking-service` под пиковый трафик.
- Разгрузка боевой БД: аналитика работает по событиям в отдельном хранилище.
- Быстрые итерации и низкий порог входа для команды на Python.
- gRPC-контракт даёт строгую типизацию взаимодействия с монолитом.

**Минусы:**
- Появляется второй язык (Python) и второй рантайм в эксплуатации — нужны новые пайплайны и мониторинг.
- Данные о бронированиях распределяются между двумя БД — требуется стратегия миграции и согласованности (eventual consistency).
- Сетевые вызовы (gRPC/REST) вместо in-process — добавляются задержки и точки отказа (компенсируется retry/circuit breaking в Task 5).

**Риски:**
- Отклонение от Kafka может потребовать пересмотра на этапе целевого состояния — mitigated брокер-независимым контрактом событий.
- Зрелость библиотек под Python 3.14 — mitigated фиксацией версий и Pydantic v2.
